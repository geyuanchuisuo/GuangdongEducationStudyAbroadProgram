## 0. 公共约定

### 0.1 认证方式

所有需登录接口在 Header 中携带：
```
Authorization: Bearer <access_token>
```

### 0.2 错误码总表

| 错误码 | 含义 |
|--------|------|
| 200 | 成功 |
| 40001 | 用户名或密码错误 |
| 40002 | 参数验证失败 |
| 40003 | 账号已被禁用 |
| 40004 | 手机号已注册 |
| 40005 | 验证码错误或已过期 |
| 40101 | 未登录或Token过期 |
| 40102 | Token无效 |
| 40301 | 无权限访问 |
| 40401 | 资源不存在 |
| 40901 | 数据冲突（重复提交或状态已变更） |
| 50001 | 服务器内部错误 |
| 50002 | AI服务调用失败 |
| 50003 | 文件存储服务异常 |

### 0.3 分页参数

```
?page=1&page_size=20&sort_by=created_at&sort_order=desc
```

### 0.4 用户类型枚举

| 值 | 含义 |
|----|------|
| PROSPECT | 客户/访客 |
| STUDENT | 学生 |
| EMPLOYEE | 员工 |
| MANAGER | 管理层 |
| ADMIN | 管理员 |

| 值 | 含义 |
|----|------|
| NEW | 新录入 |

| STRONG | 意向强烈 |

### 0.6 审批业务类型枚举

| 值 | 含义 |
|----|------|

### POST /employee/reports — 提交日报（v6.3.0 支持草稿）

**请求体**：
```json
{
  "report_date": "2026-10-17",
  "content": "今日完成...",
  "status": "submitted"
}
```

**status**：`draft`（草稿）/ `submitted`（正式提交，默认）
**迟报规则**：report_date=今天正常；=昨天可补提（is_late=true 免审批）；≤前天禁止直接提交（40002），须先存草稿走补报审批
**草稿覆盖**：同员工同日期已有 draft 时再次提交 → 覆盖内容并转正

### POST /employee/reports/{report_id}/late-apply — 日报补报申请（v6.3.0）

**请求体**：`{"approver_id": 2}`（须 MANAGER）
**前置**：日报为 draft 且 report_date ≤ 前天；重复申请报 40901；通过后日报状态 → late_pending

### POST /employee/reports/late-review — 补报审批（v6.3.0，MANAGER）

**请求体**：`{"approval_id": 1, "action": "approved", "comment": "同意"}`
**动作**：approved → 日报转正 submitted + is_late=true；rejected → 退回 draft

### PATCH /employee/customers/{customer_id}/status — 更新客户状态（6 态流转，v6.2.0）

**请求体**：
```json
{
  "status": "跟进中",
  "reason": "电话沟通后客户表现出兴趣"
}
```

**状态机约束**：新录入→跟进中/已流失；跟进中→意向强烈/已流失；意向强烈→已签约/已流失；已签约→已入学/已流失；已入学→已流失；已流失→跟进中

### GET /employee/customers — 我的客户列表（数据隔离 + 筛选排序，v6.2.0；v6.6.0 参数增强）

**Query 参数**：status / source_channel / score_min / `last_follow_start` / `last_follow_end`（最后跟进时间范围，含当天，仅命中已有跟进的客户）/ `employee_id`（**仅 MANAGER 生效**，按员工下钻查看其名下客户）/ sort_by（created_at/updated_at/score）/ page / page_size

**数据隔离**：员工只能看自己名下客户，MANAGER 看全部；MANAGER 可传 employee_id 下钻到具体员工（「按经理负责团队下钻」随二期角色拆分 MANAGER_DIRECTOR 实现）

**响应 items 字段**：id / phone / wechat / name / gender / age / education / source_channel / status / owner_employee_id / last_follow_at / assessment_score / **recommended**（最新研判的 recommended_json，推荐项目与理由，无研判时 null）/ created_at

### POST /employee/agent/chat — 企业助手会话（v6.5.0，权限感知 + 降级）

- **权限**：EMPLOYEE / MANAGER
- **请求体**：

```json
{
  "message": "帮我看看今天有什么要做",
  "session_id": "new"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| message | string | 是 | 用户消息（1~4000 字） |
| session_id | string | 否 | 会话 ID；不传或 `new` 表示新会话 |

- **权限感知注入**：后端按当前用户角色构建 Dify inputs（user_type / user_id / real_name / data_scope=own\|all / capabilities 能力清单），EMPLOYEE 仅名下数据 8 项能力，MANAGER 全域数据 14 项能力
- **响应 data**：

```json
{
  "reply": "……",
  "session_id": "conv-xxx",
  "source": "dify"
}
```

| source | 含义 |
|--------|------|
| dify | AI 网关正常返回（Dify EMPLOYEE Agent） |
| fallback | Dify 不可用，降级返回角色能力清单 + 指令式接口引导 |

- **多轮对话约定（v2.5.0 补记）**：后端透传 session_id（→Dify conversation_id）维持会话上下文，**后端不设轮次硬限制**；Dify EMPLOYEE Agent 记忆窗口建议配置 **5 轮**（覆盖指令式短链路场景；客户信息收集由多格式录入+注册表单承接，不依赖多轮问询；体验不足时仅需调整 Dify 侧配置）
- **意图边界约定（v2.5.0 补记）**：涉及薪资、人事任免等非授权指令，Agent 返回「权限不足/请联系HR」——EMPLOYEE Agent prompt 配置项，Dify 部署时落实

  "psych_alerts_pending": 0,

#### PUT /notifications/read-all — 全部标记已读

### 8.3 文件存储

#### POST /files/upload — 上传文件

**请求**：`multipart/form-data`
- `module`: crm | cs | employee | student | report | system
- `file`: 文件（<= 20MB，白名单类型）

**响应 data**：
```json
{ "object_name": "crm/2026-10-16/abc123_file.pdf", "file_url": "https://..." }
```

#### GET /files/download?object_name=xxx — 下载文件

#### GET /files/presigned?object_name=xxx — 获取预签名URL

### 8.4 操作日志查询（v6.6.0 已实现，提前落地 Phase 1.3 规划）

#### GET /operation-logs — 操作日志列表（MANAGER）

**需求依据**：员工业务需求 v2 管理层「操作日志：关键操作留痕（客户状态变更/审批/权限调整）」

**Query 参数**：`action_type`（操作类型，如 customer_status_change/customer_reassign/phone_reveal）/ `operator_id`（操作人）/ `start` / `end`（时间范围，含当天）/ page / page_size

**写入侧**：客户状态变更（customer_status_change）、客户再分配（customer_reassign）、电话查看（phone_reveal）均写 sys_operation_log

### 8.5 事件总线（内部接口，不对外暴露）

事件通过 `event_bus.publish()` 在代码内部发布，不通过 HTTP 接口。
