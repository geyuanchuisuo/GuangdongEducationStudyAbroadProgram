**第一部分 · 一期：知识库混合检索（v6.12.0，已交付）**

<a id="sec-1"></a>
## 1. 背景与目标

- 客服 Agent（Dify Chatflow）需要一个**可靠的知识检索数据源**。Dify 1.16 自带知识检索
  三路径在本机实测不可用（keyword_search 500 / 中文全文 0 命中 / semantic 需 embedding，
  见 AGENTS.md v6.11.21 / LOG-077），FAQ 长期靠 prompt 内嵌速查表顶替，不可扩展。
- 一期目标：把教育服务三类资料存入 **Milvus 向量库**，实现**混合检索**
  （稠密语义 + BM25 关键词），并在后端新增**知识检索接口**（独立 `/knowledge`，公开）。
- 明确不做（一期）：Dify Chatflow 对接（二期单独审批）、LLM 生成式回答（RAG 组合层）。

<a id="sec-2"></a>
## 2. 现有基础设施（零新建部署）

| 组件 | 现状 | 位置 |
|---|---|---|
| Milvus | v2.6.24 standalone（etcd + minio），SDK 端口 19530，WebUI 9091 | `vector/`（start.bat 一键启动） |
| 嵌入模型 | Ollama + bge-m3，稠密 1024 维（已验证） | `backend/scripts/test_bge_m3_ollama.py` |
| 文档解析 | python-docx / openpyxl / pymupdf 已是后端依赖 | `app/assessment/file_parsers.py` |

新增依赖仅 `pymilvus>=2.6,<3`。

<a id="sec-3"></a>
## 3. 总体架构

```
docs/教育服务/{公司信息,公司业务,留学政策}
        │  解析（md 标题/docx Heading/xlsx 问答行）
        ▼
     结构化切片（FAQ 整对切 / 长文 ~500 字滑窗重叠 80）
        │  Ollama bge-m3 稠密嵌入（1024 维）
        ▼
Milvus collection「yuejiao_knowledge」
  dense(HNSW/COSINE) + sparse(BM25, jieba 中文分词) + 元数据
        │  hybrid_search 双路召回 → RRFRanker(k=60) 融合
        ▼
POST /api/v1/knowledge/search（公开）→ 客服 Agent / 前端 / 二期 RAG
```

双路分工：稠密向量负责语义泛化（"学费贵不贵" ↔ "四年学费总计约30万"），
BM25 负责关键词精确命中（"2+2"、"IHK/HWK" 等专有名词）——FAQ 资料中大量
数字与项目代号场景下单靠向量容易漏。

<a id="sec-4"></a>
## 4. Milvus collection 设计

collection 名：`yuejiao_knowledge`（配置键 `MILVUS_COLLECTION`）。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | Int64 自增主键 | |
| chunk_id | VarChar(64) | 内容哈希 md5(category\|doc_type\|content)，天然去重 |
| content | VarChar(4096)，enable_analyzer + jieba | 切片全文（FAQ 为"问题\n答案"） |
| category | VarChar(32)，**partition key** | 公司信息 / 公司业务 / 留学政策 |
| source_file | VarChar(256) | 来源文件名（导入幂等的按文件清理键） |
| section | VarChar(512) | 标题路径（FAQ 为原问题） |
| doc_type | VarChar(16) | faq / doc |
| dense | FloatVector(1024) | bge-m3，HNSW(M=16, efC=200) + COSINE |
| sparse | SparseFloatVector | Milvus 内置 **BM25 Function**（输入 content）自动生成，SPARSE_INVERTED_INDEX + IP |

说明：
- 稀疏侧不用 bge-m3 的 sparse 输出——Ollama embed 接口只吐稠密向量，取 sparse
  需本地跑 FlagEmbedding（torch 全家桶），一期不值；Milvus 内置 BM25 + jieba
  对本批资料足够，二期可升级 learned sparse。
- partition key = category：按类过滤时自动分区裁剪。

> ⚠ 实施勘误（2026-10-24 实测，详见 LOG-115）：中文分词器名为 `jieba`（非 `chinese`）；
> BM25 输出字段索引 metric 必须为专用值 `BM25`（非 `IP`），上表 sparse 行以实际实现为准。

<a id="sec-5"></a>
## 5. 切片策略（`app/utils/knowledge_chunker.py`）

- **FAQ 问答对**（《常见问答对.xlsx》，37 对）：一问一答一个切片，不切碎；
  《问答对文本版.txt》为 xlsx 文本副本，导入时跳过避免重复；
- **Markdown**（企业信息.md、公司新人指南.md）：按 `#`~`######` 标题层级切 section，
  标题路径（前 3 级）并入切片首行提升召回；
- **docx**（4 个指南）：按 Heading/标题 样式切 section，表格行转「单元格 | 单元格」
  并入当前 section；
- 超长 section：~500 字滑窗、重叠 80 字、优先句子边界（。！？；换行）断开；
- 每片带元数据 category / source_file / section / doc_type。

总量估算：全部资料约 10~15 万字 → 约 300~500 个切片，standalone 内存占用 <10MB。

<a id="sec-6"></a>
## 6. 导入脚本（`backend/scripts/ingest_knowledge.py`，手动执行）

```bash
# backend 目录下；前置：vector/start.bat（Milvus）与 Ollama bge-m3 已启动
python -m scripts.ingest_knowledge            # 全量导入（幂等）
python -m scripts.ingest_knowledge --dry-run  # 只解析统计，不写库
```

幂等实现：每个文件导入前按 `source_file == "文件名"` 删除旧切片再插入；chunk_id
为内容哈希，同内容不会重复入库。资料更新后重跑即可对齐。

<a id="sec-7"></a>
## 7. 接口契约

`POST /api/v1/knowledge/search`（公开，客服 Agent 公开主页使用，与 /cs/faq 同级）：

```jsonc
// 请求
{ "query": "新加坡本硕连读学费多少", "top_k": 5,
  "categories": ["留学政策"],   // 可选，公司信息/公司业务/留学政策
  "with_score": true }

// 响应（统一 success_response 包装）
{ "code": 200, "data": {
    "kb_source": "milvus",       // milvus=正常；unavailable=向量库/嵌入不可用（空结果，不报500）
    "items": [ { "content": "…原文切片…", "category": "留学政策",
                 "source_file": "新加坡留学政策指南.docx", "section": "费用说明",
                 "doc_type": "doc", "score": 0.83 } ],
    "total": 5 } }
```

错误：未知 categories 值 → 40002（参数验证失败）；query 空/超 512 字 → Pydantic 校验拒绝。

## 13. 三期落地记录：双集合检索 + 问题改写层（v6.14.0，2026-10-27）

需求方确认（2026-10-27，四项决策）：**独立 FAQ 库（问题单独向量化）**、**并行检索 + RRF 融合**、**DeepSeek 改写 + 智能路由**、**展示改写结果**。

### 13.1 双集合检索

- **新集合 `yuejiao_faq`**（配置键 `MILVUS_FAQ_COLLECTION`）：question（jieba/BM25 输入）+ answer（纯存储不向量化）+ dense（**仅 question** 的 bge-m3 向量，问题-问题匹配更准）+ chunk_id/category（partition key）/source_file；
- **原集合 `yuejiao_knowledge` 剔除全部 FAQ**，只留 74 条长文切片（导入脚本对 xlsx 同时清理两库，迁移幂等）；
- **`search_dual`**：两集合并行检索（线程池，延迟取最慢一路）→ 内容哈希去重 → RRF(k=60) 统一融合排序；单库失败不影响另一路，全部失败才 unavailable；
- `KnowledgeItem` 新增 `source` 字段（"faq"/"knowledge"）；`/search` 默认走双集合，响应向后兼容（纯增量字段）。

### 13.2 问题改写层（`app/services/query_rewriter.py`）

- **智能路由（规则，0 延迟跳过）**：超短查询（<6 有效字符，保护 IHK/2+2/B1 类专有名词）、已含疑问结构的规范问句；实测 "IHK" 0ms 直查；
- **DeepSeek 改写**（复用 DIFY_MODEL_*，温度 0.1）：实测「想去新加坡读书那个本硕连读」→「新加坡本硕连读项目有哪些，申请条件是什么？」（~1.2s）；
- **快速失败回退**：网关失败/超时/输出为空 → 用原问题检索（改写是增强项不是依赖项）；
- **改写对库、回答对人**：改写问题只用于检索；生成回答的 prompt 里"来访者的问题"仍是用户原话；
- **可见性**：`meta`/`done` 事件新增 `rewritten_query`（未改写为 null）与 `was_rewritten`，前端回答上方显示「已理解为：XXX」小字，用户可纠偏。

### 13.3 实施期修复的三个缺陷（详见 LOG-117）

1. **10054 断连根因**：`localhost` 在本机解析为 IPv6(::1) 而 Milvus/Ollama 只监听 IPv4——config 默认值与 .env.example 全部改 `127.0.0.1`，并给嵌入批次加 2 次重试 + 逐条兜底（网络韧性）；
2. **改写输出为空**：deepseek-flash 是推理模型，`max_tokens=100` 全被思考链耗尽——去掉限额、剥 `<think>` 块、只取 content（reasoning_content 是思考文本不作检索问句）；
3. **原库 FAQ 未剔除**：导入脚本 FAQ 分支漏调长文库 delete_by_source——补上后重跑迁移验证干净。

### 13.4 验收（2026-10-27 实机）

双集合检索 FAQ 问句两库结果 RRF 交错；改写路由三例符合预期；完整链路 meta 带改写字段、来源混含 faq+doc、answer_source=model、首字 4.5s/总 6.4s，回答数字与知识库一致。pytest **202/202**（+11：路由规则/改写回退/RRF 融合/单库降级）、npm build ✓、verify_all 30/30。路由 118 paths 不变，依赖零新增，config 仅追加 1 键。
