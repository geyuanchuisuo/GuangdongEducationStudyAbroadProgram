> 评级口径：≥80% 优秀｜60–79% 良好｜40–59% 一般｜<40% 较差。综合得分为四指标等权平均。

**辅助指标**：检索命中率 100%（36/36 问题均召回到内容）、模型作答率 100%（全部走真实生成，无降级）、拒答准确率 100%（3 道超纲题全部正确拒答）。

**一句话结论**：系统检索召回充分、回答高度切题、无实质性幻觉；唯一真实缺陷是「官方邮箱/网址」这一条窄问题未召回联系方式切片（详见第四节），其余低分均为指标口径造成的正常扣分，而非系统错误。

## 二、评测设计

### 2.1 评测集（golden set）
- 规模：**36 题**（标准版），覆盖三大知识域 + 拒答能力。
- 构成：
  - 公司信息（8 题，id 1–8）
  - 公司业务（16 题，id 9–24）
  - 留学政策（9 题，id 25–33）
  - 拒答能力（3 题，id 34–36，知识库无答案，考察是否乱编）
- 每题含：question、ground_truth（逐字取自知识库原文，保证标准答案准确）、relevant_docs（来源文件）。

### 2.2 评测链路（in-process，直连生产代码）
评测脚本 import 生产服务本体（不改业务代码、不启 HTTP 服务），完整复现线上问答链路：
```
问题 → query_rewriter.rewrite（改写对库）
     → knowledge_service.search_dual（双集合混合检索 top_k=5）
     → _build_messages（受限 Prompt，回答对人）
     → knowledge_qa_service._chat_gateway（deepseek-flash 生成）
```

### 2.3 RAGAS 四指标
| 指标 | 衡量什么 | 计算方式 |
|------|---------|---------|
| Context Precision | 检索到的切片中，与标准答案相关的排在前面吗 | LLM 逐切片判定相关性并加权 |
| Context Recall | 标准答案的信息，检索有没有捞全 | LLM 以 ground_truth 为参考比对 |
| Faithfulness | 回答有没有编造检索内容之外的信息 | LLM 拆句，逐句核对是否有上下文支撑 |
| Answer Relevancy | 回答是否切题、完整回应问题 | LLM 反向生成问题比对相关性 |

> 说明：本次 LLMContextPrecisionWithReference / LLMContextRecall 以 ground_truth 文本为参考基准（reference-based），而非人工标注的文档 ID 集合；这与「relevant_docs 仅作来源留档」的设计一致。

## 四、低分归因（关键）

### 4.1 唯一真实缺陷：id=8「官方邮箱和网址」检索未命中
- **现象**：cp=0、cr=0、ar=0；系统回答「知识库中未找到相关内容」。
- **根因**：`企业信息.md` 的联系方式切片（含邮箱 postmaster@ges1981.com、网址 http://www.gdjyfw.cn）未进入该问法的 top-5。
- **佐证**：id=6「地址和联系电话」**同样问联系方式**，却成功召回了该切片并正确答出邮箱/网址——证明信息在库内、可被召回，只是「邮箱和网址」这一措辞的向量/BM25 匹配度不够，被排在 top-5 之外。
- **判断**：模型拒答是**正确行为**（没捞到就不编），属检索排序问题，非生成问题。
- **建议**（择一）：
  1. 在 `常见问答对.xlsx` 补一条 FAQ：「粤教服务的官方邮箱和网址是什么？」→ 直接命中 FAQ 集合（问题-问题匹配，最稳）。**推荐**。
  2. 优化 `企业信息.md` 联系方式块的切片粒度，让「邮箱/网址」与其关键词聚在同一可召回单元。

### 4.2 Faithfulness 未满分的扣分（ids 3/5/8/9/11/13/15/27）
- **性质**：**非幻觉**。核心事实全部正确。
- **原因**：回答普遍在末尾追加了「建议联系顾问进一步咨询」这类引导话术，以及少量基于常识的补充说明（如 id=5 使命内涵展开、id=9 项目说明），这些文字未逐字出现在被检索切片中，被 Faithfulness 判为「无上下文支撑」。
- **判断**：属可接受的产品化表达。若追求指标好看，可在 Prompt 中收敛尾注/补充，但会牺牲体验，不建议为此改。

### 4.3 Context Precision 偏低的扣分（ids 4/6/13/21/24）
- **性质**：**top_k=5 的正常副作用**。
- **原因**：这些是「窄问题」（如「主营业务有哪些」「专业类别有哪些」），答案只需 1–2 个切片，但检索固定返回 5 条，多出的切片虽非错误、却稀释了精确率。
- **判断**：召回率为满分（信息全捞到了），精确率被摊薄属预期。若在意可对简单事实类问题动态调低 top_k 或加 rerank。

## 六、检索 vs 生成 分析

- **检索层**：召回率 96.97%、命中率 100%，双集合（knowledge 74 + faq 36）+ RRF 融合表现稳健；仅 id=8 一条窄问法排序未进 top-5，为唯一可操作缺陷。
- **生成层**：答案相关性 94.40%、忠实度 85.67%，受限 Prompt 有效抑制幻觉（除 id=8 因无检索内容拒答外，33 题事实全部正确）；忠实度扣分集中在尾注引导语与常识性补充，非事实错误。
- **降级链**：36 题全部 `answer_source=model`（真实生成），未触发 retrieval_only / unavailable，说明网关、Ollama、Milvus 全链路稳定。

## 七、改进建议（按优先级）

1. **【P0，唯一真实缺陷】** 在 `常见问答对.xlsx` 补 FAQ：官方邮箱和网址 → 修复 id=8，预计综合分升至 ~91%+。
2. **【P2，指标优化】** 对简单事实类问题动态调低 top_k 或加 rerank，缓解窄问题 Context Precision 被摊薄（ids 4/6/13/21/24）。
3. **【P3，可选】** 若追求 Faithfulness 好看，可在 Prompt 收敛「建议联系顾问」尾注；但会牺牲引导体验，不建议为指标而改。

## 八、评测环境与口径说明（重要）

- **隔离环境**：评测在独立虚拟环境 `evaluation/.venv`（Python 3.11）内进行，**未修改**业务代码、数据库、向量库，也未触碰 `backend/pyproject.toml` / `uv.lock`。评测对生产完全只读。
- **自评偏差**：判定模型 deepseek-flash 与生成模型同源，存在 LLM 自评的潜在乐观偏差；建议关键版本复评时引入异构判定模型交叉验证。
- **strictness=1**：AnswerRelevancy 因模型网关仅支持 n=1，strictness 设为 1（默认 3），单轮判定方差略高。
- **reference-based 口径**：Context Precision/Recall 以 ground_truth 文本为参考，未使用人工标注文档 ID 集合。
- **评测脚本**：`evaluation/run_eval.py`（可复跑，支持 `--limit` / `--skip-ragas`）；原始结果落盘于 `evaluation/results/`（pipeline_raw.json、ragas_per_question.csv、ragas_result.json、summary.json）。
