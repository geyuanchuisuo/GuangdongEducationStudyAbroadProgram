## 一、结论摘要

前端可以完善输入校验、错误提示、加载状态和降级展示，但不能替代后端接口、数据库约束、权限控制、环境变量和外部 AI 服务。当前最需要后端处理的是：

| 优先级 | 问题 | 当前表现 | 前端为何无法根治 | 负责模块 |
|---|---|---|---|---|
| P0 | 成绩修改接口缺失 | 前端调用 `PUT /employee/scores/{score_id}`，后端只有创建和查询 | 前端无法自行提供服务端持久化接口 | M3 员工模块 |
| P0 | 成绩重复录入缺少服务端约束 | 同一学生、课程、学期可被重复提交 | 前端校验存在并发绕过和直接 API 调用绕过 | M3 + 数据库 |
| P1 | 成绩范围口径不一致 | 前端限制 0-100，后端 `ScoreCreate` 允许 0-999.99 | 业务规则必须由后端最终裁决 | M3 |
| P0 | 三个 Dify Agent 配置/服务未闭环 | 本地 `.env` 仍为占位 Key，Dify 服务不可达时只能降级 | 密钥、服务地址、网络和应用发布均不在前端职责内 | M0 AI 网关 + 运维 |
| P1 | 本地数据库配置与标准配置不一致 | `.env` 为 3306/123456，Docker/示例为 59000/420821 | 前端无法决定后端实际连接哪个数据库 | 后端 + 运维 |
| P2 | pytest 连接清理警告 | 4 个 `aiomysql` 事件循环关闭后清理警告 | 属于后端测试夹具和连接生命周期 | 后端测试 |
| P2 | 后端规则缺少自动化回归 | 新增成绩交互目前主要依赖接口冒烟 | 前端构建无法覆盖服务端约束和权限 | M3 测试 |

## 二、问题明细与后端解决方式

### 1. 成绩修改接口缺失（P0）

**现状证据**

- 前端：`frontend/src/api/platform.ts` 已调用 `PUT /employee/scores/{score_id}`。
- 后端：`backend/app/api/v1/employees.py` 当前只有 `POST /scores` 和 `GET /scores`。
- 当前 OpenAPI 为 103 paths（102 API + 1 health），没有成绩修改路径。

**为什么前端解决不了**

前端只能发起 HTTP 请求。若后端没有对应路由，请求只能返回 404/405；前端无法安全地修改数据库记录，也不应绕过 API 直接操作数据库。

**后端建议**

1. 新增 `PUT /api/v1/employee/scores/{score_id}`。
2. 新增 `ScoreUpdate` 请求模型，字段为 `score`。
3. `EmployeeService.update_score()`：
   - 校验成绩记录存在，否则返回 `404`；
   - 校验 `score` 范围；
   - 校验当前用户为 EMPLOYEE/MANAGER；
   - 明确员工的数据权限边界；
   - 修改后提交事务并返回 `ScoreOut`。
4. 为该路径补充 OpenAPI 和权限测试。

**验收标准**

- 修改存在的成绩返回 `200`。
- 不存在的 `score_id` 返回 `404`。
- 超出业务范围返回 `422`。
- 无权限角色返回 `40301`。
- `verify_all` 能识别新增路径。

### 2. 成绩重复录入缺少服务端约束（P0）

**现状证据**

- 前端可以在客户端提示“重复请编辑”，但当前后端 `record_score()` 没有唯一性检查。
- 浏览器之外的 Postman、脚本、并发请求都可以重复提交。

**为什么前端解决不了**

前端校验只发生在单个浏览器会话中，无法保证：

- 两个员工同时提交；
- 用户直接调用 API；
- 自动化脚本重复写入；
- 页面刷新后重复点击。

**后端建议**

1. 明确唯一键：`student_id + course_name + semester`。
2. `semester` 为空时必须规范化，不能依赖 MySQL 可空唯一索引允许多条 NULL。
3. 优先在数据库增加唯一约束，再在服务层捕获冲突并返回 `40901`。
4. 创建接口使用事务和唯一索引保证并发安全。
5. 修改接口也必须防止改成与已有记录冲突。

**验收标准**

- 重复创建返回 `40901`。
- 并发创建最多成功一条。
- 修改到已有组合时返回 `40901`。
- 数据库层可以直接阻止重复数据。

### 3. 成绩范围口径不一致（P1）

**现状证据**

- 前端成绩输入和编辑限制为 `0-100`。
- `backend/app/schemas/employee.py` 的 `ScoreCreate.score` 当前为 `ge=0, le=999.99`。
- 后端尚未提供 `ScoreUpdate`。

**为什么前端解决不了**

前端控件限制可以被修改、绕过或直接通过 API 调用绕过。最终业务范围必须由后端模型、服务和数据库共同约束。

**后端建议**

1. 由业务确认成绩上限：当前前端口径为 100。
2. `ScoreCreate.score` 和 `ScoreUpdate.score` 同步改为 `ge=0, le=100`。
3. 数据库列增加合理约束或服务层统一校验。
4. 添加 0、100、-0.1、100.1 等边界测试。

### 4. 三个 Dify Agent 配置/服务未闭环（P0）

**现状证据**

- 本地 `backend/.env` 中三个 Agent Key 仍是占位值。
- 当前模型兜底配置仍需有效的模型 Key、模型地址和模型名称。
- 前端聊天窗口只能显示失败或本地降级结果。

**为什么前端解决不了**

Dify 连接依赖以下服务端/基础设施条件：

- Dify 应用是否创建并发布；
- 三个 `app-` 开头的真实 Key；
- `DIFY_BASE_URL` 是否指向正确入口（本机 `http://localhost:8081`，容器内 `http://dify_nginx`，见 docs/Dify部署与调用指南.md）；
- 后端容器到 Dify 的网络是否连通；
- Dify 模型供应商和模型 Key 是否有效；
- 服务端超时、重试和降级策略。

前端不能保管密钥、启动 Dify、修复容器网络或发布 Agent。

**后端/运维建议**

1. 在后端环境注入三个真实 Agent Key，禁止把生产 Key 提交到 Git。
2. 将 `.env.example`、本地 `.env`、Docker 环境变量统一。
3. 启动 Dify 后先验证 `/v1/models` 或等价健康接口。
4. 分别对客服、员工、学生 Agent 执行真实 chat 冒烟测试。
5. 保留当前服务端降级，但日志中明确 `source=dify/model/fallback`。
6. 对 Key 无效、网络失败、模型超时分别返回可诊断错误。

**验收标准**

- 三个 Agent 均返回 `source=dify`。
- 阻断 Dify 后，员工和学生助手能稳定返回 `source=fallback`，不产生 50001。
- 客服 Agent 的意图、推荐和会话记录仍能正常落库。

### 5. 数据库环境配置不一致（P1）

**现状证据**

- `backend/.env`：本地连接 `localhost:3306`，密码为旧测试值。
- `backend/.env.example`：标准配置为 `localhost:59000`，密码为 `420821`。
- `docker-compose.yml`：宿主机映射 `59000:3306`，容器内数据库密码为 `420821`。
- `scripts/create_frontend_test_accounts.py`：连接 `localhost:59000`。

**为什么前端解决不了**

前端不连接 MySQL，也不决定 Alembic、自动建表、测试账号初始化脚本实际访问哪个数据库。配置不一致可能导致“前端登录成功但账号脚本写入另一套库”。

**后端/运维建议**

1. 确定唯一标准：当前项目文档和 Docker 采用 `59000/420821`。
2. 本地 `.env` 从 `.env.example` 重新生成并核对。
3. 账号初始化脚本、Alembic、后端应用使用同一连接来源。
4. Docker、本地开发和测试环境分别验证数据库连接。
5. 生产环境通过 Secret/环境变量注入密码，不写入仓库。

### 6. pytest 连接清理警告（P2）

**现状证据**

`143 passed`，但有 4 个 `aiomysql.Connection.__del__` 在事件循环关闭后清理的警告。

**为什么前端解决不了**

这是 Python 异步数据库连接和 pytest 事件循环生命周期问题，与 Vue、TypeScript 无关。

**后端建议**

1. 测试夹具中显式关闭连接和引擎。
2. 统一 pytest 的事件循环策略。
3. 对每个测试会话使用独立的 engine/session。
4. 将警告数量纳入 CI 质量门槛。

### 7. 新增业务规则缺少后端自动化测试（P2）

**现状证据**

成绩创建、重复拦截、成绩修改主要通过接口冒烟验证，后端 pytest 尚未完整覆盖这些规则。

**为什么前端解决不了**

前端构建只能证明 TypeScript/Vue 可编译，不能证明数据库唯一性、事务并发、权限和错误码正确。

**后端建议**

新增测试至少覆盖：

- 成绩创建成功；
- 重复创建 40901；
- 成绩修改成功；
- 修改不存在记录 404；
- 成绩范围边界；
- EMPLOYEE/MANAGER 权限；
- 数据隔离；
- 并发重复写入。

## 三、前端已经完成的辅助处理

以下内容已由前端完成，但不能替代后端修复：

- 输入框限制成绩为 0-100；
- 编辑成绩前进行数值校验；
- 日报日期和内容必填校验；
- 重复成绩时提供明确提示；
- 请求失败时提供可读错误；
- 对 AI 不可用展示降级状态；
- 预览环境提供 `/api` 代理；
- 构建包分包，避免单包过大。

## 四、建议处理顺序

1. 后端补齐成绩修改接口和权限校验。
2. 数据库增加成绩唯一约束，服务层返回 40901。
3. 统一成绩范围为 0-100。
4. 统一数据库 `.env` 与 Docker 配置。
5. 配置三个 Dify Key 并完成真实 Agent 冒烟。
6. 补齐成绩/权限/并发测试。
7. 修复 pytest 连接清理警告。
8. 再做前端联调回归。

## 五、共享模块提醒

AI 网关、认证、审批引擎、事件总线、通知中心属于共用模块。涉及这些模块的修复必须先向项目负责人确认，避免影响 M1/M2/M3/M4/M5 并行开发。
