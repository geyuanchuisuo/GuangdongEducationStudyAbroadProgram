## P0 —— 必须先定的事（决定各模块能否独立开工）

### 1. 模块划分不完整：缺少"公共基础设施"归属，且缺 3 个独立基础模块

当前业务划分为：前端+研判、客户模块、员工模块、学生模块、报告模块。
对照需求文档 v4 与 客户需求明细 全景业务规则，缺少以下归属明确的基础件：

| 缺失项 | 为什么不能缺失 | 建议归属 |
| --- | --- | --- |
| 系统/用户/权限管理 | 四角色（PROSPECT/STUDENT/EMPLOYEE/MANAGER）+ 管理层逐人 permissions 配置是所有模块的地基 | 独立基础模块，不属于任何业务模块 |
| 课程/活动公共数据层 | 报名、课程为所有角色共用基础数据（客户报、学生报、报告统计报名量，B6 已确认共用同一活动表） | 独立"公共业务数据"模块，各模块通过它取数，禁止各自建表 |
| 审批工作流引擎 | 客户转留学生（经理→总裁两级，B7）、日报补报审批、学生请假审批，是 客户/员工/学生/报告 多模块的隐形桥梁 | 独立工作流模块 |

**待讨论**：
- 以上三个基础件由谁负责？（对照 20261015 下午纪要 O1：客户研判/客服推荐/智能报告尚无负责人，公共基础设施也需指派，建议归"数据架构设计"负责人——纪要里是宝哥）
- 模块负责人确认后即可冻结一期模块边界。

### 2. "客户研判"的模块归属需要定死

- 现状：研判被单列为"前端+研判"，但研判本质是**客户模块的 AI 子能力**（输入多源文件 → 匹配度打分，见需求文档 §3.2），无法脱离客户数据独立运行。
- 若研判与客户模块分属两人，跨模块取数/写数会互相依赖。
- **建议**：研判作为客户模块的 AI 子能力，客户模块负责人统筹；"前端"单独作为公共前端基础设施（统一入口 + 角色菜单 + 请求契约），不绑定研判。
- **待讨论**：是否同意上述归属；"前端+研判"这条开发线由谁负责。

### 3. 模块间解耦机制（事件契约）—— 并行开发互不影响的核心

- 现状：五个模块若都直接 `import` 彼此的 model/service，改动会互相影响；目前**完全没有**事件/消息契约。
- 员工功能矩阵里已隐含多条事件链，建议直接拿来做契约定稿素材：
  - 代客申请转化通知链：审批结果 → 站内信 + Agent 推送 → 学生端状态变更 → 员工端待办消除
  - 心理预警 → 员工端生成"心理关怀待办"
  - 投诉处理结果回流学生端
  - 客户状态变更 → 销售漏斗实时同步
- **待讨论**：
  - 采用何种解耦方式？数据量小，建议：数据库事件表 或 Redis 发布/订阅，**不要**一上来引 Kafka/RabbitMQ。
  - 先冻结一批核心事件契约（哪个模块发什么事件、带什么字段），建议至少包括：
    - `客户已注册`（客户模块 → 员工待办）
    - `客户已转化为学生`（客户模块 → 学生模块、报告模块、员工待办消除）
    - `请假已审批`（员工模块 → 学生模块、通知中心）
    - `心理预警已生成`（学生模块 → 员工/管理层待办与通知）
    - `投诉已处理`（员工模块 → 学生模块、通知中心）
  - 契约文档由谁出？建议数据架构负责人出初稿，各模块负责人签认。

### 4. 前端项目尚未初始化（仓库根目录无 `frontend/`）

- 现状：仓库里只有 `backend/`，前端一行代码都没有。前端不落地，"前端+研判"这条线无从谈起；各模块负责人也无法拿到统一的请求封装/错误码/类型定义去并行开发。
- **有利条件**：需求文档 §8.3 / §11.2 / §11.3 已给出完整的前端目录结构、三端页面清单和 Axios 封装代码（含 40101 跳登录逻辑），**照着搭即可，设计已冻结**。
- **待讨论**：
  - 前端初始化（Vue3 + TS + Element Plus + Pinia + 请求封装 + 路由 + 角色驱动菜单守卫）由谁做、何时完成？
  - 是否统一约定：各模块前端页面只调"契约接口"，不直接拼 URL、不绕过统一封装。

### 5. 权限基准三方不一致，必须定死按哪个实现（新增，高优先）

三处口径打架：

| 来源 | 口径 |
| --- | --- |
| 需求文档 §10.2（v4，已确认） | 完整权限编码矩阵（prospect.* / student.* / employee.* / manager.* 共 24 个编码），MANAGER 走 `sys_user.permissions` JSON 逐人配置 |
| 20261015 下午纪要 B4 | 一期三级权限从简，"仅做身份区分与基本隔离，不做细分权限矩阵，细化留二期" |
| 现有代码 | `User` 模型**没有 `permissions` JSON 字段**；`require_user_type` 只能按 user_type 粗判 |

**待讨论**：
- 一期到底实现到哪个粒度？建议折中：`user_type` 粗判 + 数据隔离（10.3 员工只看名下客户）落地，`permissions` JSON 字段**表结构先加上**（避免二期改表），逐人配置界面二期做。
- 若按需求文档 §10.2 全量实现，工作量重排，需确认是否压缩其他模块范围。
- 此决议直接影响所有模块的接口门禁写法，**必须先定再开工**。

### 6. 代码表结构与需求文档 v4 不一致清单（新增，高优先）

逐表比对 `models/` 与 需求文档 §9 后，存在以下漂移，需会上定"以文档为准还是以代码为准"并一次性修正：

- 客户状态机 4 态 vs 6 态定终版；功能矩阵里"客户状态变更写入操作日志"是否进一期（目前无操作日志表）。

### 7. AI 调用必须走统一网关，禁止各模块直连 Dify

- 现状：`config.py` 已配好 3 个 Dify Agent Key（STUDENT/EMPLOYEE/CUSTOMER），需求文档 §12.3 也给了 `AIService` 示例（`chat(agent_key, message, ...)`），但**后端没有任何实际接入代码**。
- 风险：5 个模块里有 4 个要调 Dify，各模块各写一遍调用逻辑，后续换协议/加限流/改 Key 要改 N 处。
- **待讨论**：
  - 按 §12.3 示例实现统一 AI 网关层（放 `services/ai_service.py`），暴露 `chat(agent, payload)` 单入口，各模块只调网关。
  - 流式（SSE）支持：Agent 窗口对话是否需要流式返回？§12.3 示例是 blocking 模式，需定终版。
  - 各 Agent 的超时/重试策略；网关归公共基础设施负责人。

### 8. 文件上传/对象存储（MinIO）接入层

- 现状：docker-compose 已起 MinIO，`config.py` 已配好连接信息，但**后端没有任何 MinIO 接入代码**。需求文档 Phase 1.1 明确"文件存储（MinIO）集成"在一期第 1-2 周。
- 客户研判（PDF/照片/Word/Excel，员工功能矩阵还要求"文件大小与页数需明确上限"）、报告附件都要走文件存储。
- **待讨论**：
  - 统一 `upload/download` 接口 + 存储路径规范（按模块/日期分目录）由谁定？
  - 上传大小/页数上限、文件类型白名单；临时研判文件与正式附件的保留策略。

### 9. 数据权限（员工数据隔离）无统一实现

- 现状：需求文档 §10.3 明确"普通员工只能查自己名下客户（`crm_lead.owner_employee_id = 当前用户ID`）"，员工功能矩阵进一步要求组织架构联系方式脱敏（二次确认才展示完整电话）。目前**没有任何集中实现**。
- 风险：客户/员工/报告三个模块都会写数据过滤，各写一套口径必然不一致。
- **待讨论**：
  - 做一个**统一数据权限组件**（依赖注入 + 查询装饰器），各模块挂上即生效；由公共基础设施负责人实现。
  - 一期最小门禁清单：哪些接口必须做角色/数据隔离（客户查询、研判结果、报告、审批）——建议按需求文档 §3.5 员工视图矩阵逐条过一遍。

### 10. 两套建表机制冲突：`create_all` vs Alembic

- 现状：
  - `main.py` 启动时 `Base.metadata.create_all` 自动建表；
  - `migrations/` 目录只有 `env.py` + mako 模板，**没有 `versions/` 实际迁移版本**；
  - AGENTS.md 写"应用启动时自动创建所有17张表，无需手动执行迁移"。
- 风险：多人并行改表结构时，`create_all` 不会改已存在的表（只建新表），而 Alembic 迁移是版本化演进；两套并存迟早打架。P0-6 的表结构对齐修正必须走这条机制。
- **待讨论**：
  - 建议：开发期保留 `create_all` 图方便，但**任何表结构变更必须走 Alembic 迁移**并签入 `versions/`；生产只认迁移。
  - 迁移统一由谁签？建议公共基础设施负责人统一管 `migrations/versions/`。

### 11. 测试数据初始化是一期交付前提，但脚本不存在（新增）

- 员工功能矩阵"公共能力·数据"原话：**"数据库直接录入足量测试数据，可立即进入测试——一期交付前提"**。
- 需求文档 §16 只给了 5 个种子账号的 SQL 草案；`scripts/` 目录（init_db.py / seed_data.py）**不存在**。
- 报告模块 5 类报告、经营看板、工作台 KPI（新增意向数/转化率/在办学生数/投诉率）没有足量测试数据无法验收。
- **待讨论**：
  - 种子数据量级定多少（每类客户/学生/日报/投诉各多少条）？由谁出脚本（建议数据架构负责人）？
  - 注意"数据初始化"与"数据导出（Excel）"（功能矩阵公共能力）都要进一期，字段口径需对齐。

## P1 —— 模块开工前应完成的"公共地基"（P0 完成后约 1 周内）

### 12. 审批工作流最小实现（范围比原设想大）

一期确认项与功能矩阵合并后，一期审批场景实际有 **4 种**：

| 场景 | 链路 | 来源 |
| --- | --- | --- |
| 客户转留学生 | 员工申请 → 经理审批（两级：经理→总裁，B7） | 需求文档 §3.1.2 / 纪要 B7 |
| 学生请假 | 学生提交 → 负责员工单层审批 | 需求文档 §3.3.1 |
| 日报补报 | 次日 0 点后提交 → 需经理审批补报 | 员工功能矩阵（**需求文档未包含，需补进一期范围**） |
| 批量审批 | 转化申请支持批量通过 | 员工功能矩阵 |

- **待讨论**：
  - 一张通用"审批单"表 + `发起/审批/驳回/批量` 接口 + 可配置链路，上述 4 场景全部调它，**禁止各自实现审批**。
  - 驳回后行为：退回修改 or 重新发起？是否允许加签？（下午纪要 O6 仍未决）
  - 请假规则：同一学生同一时间段已有请假记录时提示"审批中/已通过"（功能矩阵规则）。
  - 审批结果通过事件（见 P0-3）通知发起人与相关方。

### 13. 站内消息/通知中心（`sys_notification`）

- 需求文档 §9.1.17 有完整 DDL（6 类通知类型：审批结果/待办提醒/学业提醒/心理预警/状态变更/系统），但 `models/` 中**没有对应 ORM 类与 import**。
- 各模块的待办提醒、预警、审批结果推送都依赖通知中心；功能矩阵还要求"Agent 不可用时站内信兜底"。
- **待讨论**：
  - 确认补建 `sys_notification` 模型 + 统一 `notify(user_id, type, content)` 服务接口。
  - Agent 主动推送（学生/员工登录后）与站内消息是同一通道还是分两条？提醒定时任务（DDL 提前 N 天、学业 reminder_sent 标记）归谁做？

### 14. 课程/活动公共数据服务

- 现状：`course.py`/`event.py` 模型已有，但接口均未实现（路线图 2.7/2.8）。

  - 报名与客户转化是否自动联动（O5 未决）：建议一期只做记录不做自动联动，二期评估。

### 15. 统一 API 契约（错误码 / 分页 / 类型）推广到所有模块，并修代码

- 现状：`schemas/common.py` 已有 `PageParams/PageResult` 雏形，但代码 `ERROR_CODE_MAP` **缺 40005（手机号格式错误）、40102（Token无效）**，与需求文档 §14.3 完整错误码表不一致；需求文档 §14.3 还定义了 40901（客户重复录入冲突）而代码没有。
- **待讨论**：
  - 各模块新接口**必须**沿用统一响应格式与 §14.3 错误码表；公共基础设施负责人出一份《接口契约 v1》文档。
  - 前端 TS 类型从 OpenAPI 自动生成还是手工维护？建议自动生成。

### 16. 各模块负责人确认（承接下午纪要 O1）

- 客户研判、客服推荐（并入客户模块）、智能报告 三个模块至今无负责人；公共基础设施（P0/P1 各项）也需指派。

## P2 —— 可并行收尾项（P0+P1 完成后即可各模块独立推进）

### 17. 智能报告模块的数据来源边界 + 缺失数据源（新增）

- 原则：报告模块**只调各模块已暴露的查询接口取数，不直接查别人的表**（否则表一改报告就崩）。
- **缺口**：员工功能矩阵管理层工作台 KPI 包含"**签约金额**"，但 17 张表里没有任何签约/缴费/金额表；`crm_lead` 也没有金额字段。若一期经营看板要展示签约金额，必须先定数据源（新建签约表？还是仅记录不统计？）。
- 待讨论：
  - 签约金额数据源定论；若一期不做，工作台 KPI 相应下线或标注"暂无数据"。
  - 情绪评估"只记录不评分"（B5）与报告统计口径（O4）：定聚合口径（提交量、情绪标签分布等，不呈现个体名单）。
  - 报告触发方式（定时 or 手动）；生成物存 `ai_report` 表 + 附件走 MinIO 公共层（P0-8）。

### 18. 学生心理数据进入报告的合规口径

- 下午纪要 C.2-3 风险：号码、未成年人个人信息与情绪记录同时进经营报告，合规改造后置成本高（B8 已确认一期接受为已知风险）。
- **待讨论**：一期至少约定脱敏与授权口径（心理周报不出现个体名单，用聚合口径），避免二期推倒重来。

### 19. 时间节点与里程碑
