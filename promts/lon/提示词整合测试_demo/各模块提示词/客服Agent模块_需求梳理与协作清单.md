# 客服 Agent 模块（P2 · 客户侧）需求梳理与协作清单

> 负责人：p2（你）
> 模块定位：教育 AI 中台的**对外获客转化入口**
> 本文档用途：把「我要做什么、注意什么、和谁配合」一次说清，可直接作为需求文档 / 开发设计文档的基础素材。

---

## 一、模块定位与在业务链路中的位置

```
客户研判 ──► 【客服 Agent】──► 企业智能助手 ──► 学生智能助手
（筛选合格线索）  （对外获客·答疑·推荐·报名）  （对内销售/教务运营）   （在读服务）

                        └──────────► 智能报告（管理层决策）
```

- **上游输入**：客户研判（P1）判定为「符合机构目标画像」的合格线索，是客服侧的客户来源。
- **下游输出**：客服会话中的**高意向客户**要回流成 `crm_lead` 意向客户，交给企业智能助手（P3）跟进转化。
- **在本模块内闭环**：咨询 → 答疑 → 推荐 → 报名 → 报名信息回写后台。
- **一句话职责**：把机构原本靠人工客服跑的「答疑 → 推荐 → 引流 → 报名预约」流程，搬到统一对话入口上，并把访客变成可分析、可跟进的客户数据资产。

**⚠️ 最容易做错的地方**：客服 Agent 不是「一个聊天机器人」，而是「**一个对话入口 + 4 类结构化数据落库 + 1 条导流链路**」。如果只做问答不落数据，P5 的客户经营报告就没有原料，整个链路断掉。

## 二、7 大场景需求逐项拆解

对照甲方《客户需求表》「客服Agent」需求项，7 个场景逐条落到「实现方式 / 数据来源 / 交付物 / 验收点」。

### R2-1 公司信息咨询
| 项 | 内容 |
|---|---|
| 业务描述 | 解答访客关于品牌背景、发展历程、成功案例、校区分布等基础信息，建立第一层信任 |
| 知识来源 | 《企业信息》docx（粤教服务 1981 年创办、2024.3 划转粤教国际、使命愿景、部门架构、联系方式） |
| 实现方式 | **Dify RAG**（知识库检索 + 生成），严格基于知识库作答 |
| 交付物 | 知识库文档切片 + Dify 问答应用 + 检索接口 |
| 验收点 | 问「你们公司是国企吗 / 什么时候成立的 / 在哪个校区」能准确回答；知识库外的问题不编造 |

### R2-2 公司业务查询
| 项 | 内容 |
|---|---|
| 业务描述 | 回应留学申请、背景提升、语言培训等核心业务板块咨询 |
| 知识来源 | 《公司业务》两篇：**新加坡国际本硕升学计划**（2+2 / 0.5/1+2 / 2+2+1 / 6+6 / 9+6 等）、**中德精英人才共建计划**（德国双元制） |
| 实现方式 | Dify RAG + 结构化业务卡片（前端展示项目要点） |
| 交付物 | 业务知识库 + 「业务介绍卡」返回结构 |
| 验收点 | 能区分「新加坡项目」与「德国项目」的适用人群与优势，回答与原文一致 |

### R2-3 海外留学政策查询
| 项 | 内容 |
|---|---|
| 业务描述 | 各国签证要求、院校申请门槛、最新移民就业政策 |
| 知识来源 | 《留学政策》：新加坡留学政策指南、德国留学政策指南（如需扩展多国，须向甲方要更多文档） |
| 实现方式 | **Dify RAG + 强制引用来源 + 防幻觉约束**（政策/签证/费用属高风险输出，必须基于知识库，不能自由发挥） |
| 交付物 | 政策知识库 + 防幻觉 Prompt + 免责/兜底话术 |
| 验收点 | 知识库无覆盖时，回答「该问题需咨询顾问确认」而**不是编造**；有覆盖时能带出处 |

### R2-4 课程与项目推荐
| 项 | 内容 |
|---|---|
| 业务描述 | 基于客户**学历背景 + 留学意向**，智能推荐匹配的留学方案、语言课程或背景提升项目，引导进入深度咨询 |
| 数据来源 | `course_project` 课程与项目表（结构化）+ 甲方课程项目清单 |
| 实现方式 | **不能纯靠大模型**。建议：Python 后端做「规则初筛」（学历→可报项目映射），再由 Dify 生成个性化推荐话术。参考《用户画像研判规则》里的学历—项目对应关系 |
| 关键输入 | 学历层次、意向国家、年龄、预算——这些**由客服会话中抽取（槽位）**，属与 AI 能力的配合点 |
| 交付物 | 推荐接口 + 推荐卡片结构 + 规则映射表 |
| 验收点 | 输入「我是高三学生想去新加坡」能推荐 0.5/1+2 及本硕连读；输入「大专毕业」能推荐一年制专升本 |

### R2-5 活动与讲座报名（**本模块唯一的完整业务闭环，重点**）
| 项 | 内容 |
|---|---|
| 业务描述 | 查询近期线上/线下分享会、招生官见面会，并直接完成预约报名，沉淀私域流量 |
| 数据表 | `event_lecture`（活动表）、`event_registration`（报名表） |
| 实现方式 | **Python 后端 CRUD**（列表、详情、报名、名额校验、重复报名校验）+ 前端报名表单卡片 |
| 必须处理的细节 | ① 名额上限校验（`max_participants` / `current_participants` 并发安全）；② 同一客户重复报名拦截；③ 报名需**客户身份**（见第三节协作点）；④ 报名成功回写后台，员工端可查名单 |
| ⚠️ 数据缺口 | 你手上的资料里**没有「近期活动与讲座清单」**，必须尽快向甲方索要，否则 `event_lecture` 无数据、演示空跑 |
| 验收点 | 能列出活动 → 选活动 → 填表报名 → 报名人数 +1 → 员工端能查到该报名 |

### R2-6 常见问题自助解答
| 项 | 内容 |
|---|---|
| 业务描述 | 秒级回复申请流程、服务费用、退费政策等高频问题 |
| 知识来源 | 《常见问答对》xlsx / 问答对文本版（**已梳理约 37 条 QA**，覆盖公司、项目、学费、流程） |
| 实现方式 | **结构化 FAQ 优先**（相似问法匹配命中即秒回）→ 未命中再走 RAG。这比纯 RAG 更准、更快 |
| 交付物 | FAQ 结构化表 + 召回服务 + 兜底转人工话术 |
| 验收点 | 问「报名流程」「学费多少」「缴费账号」能秒回且与甲方原文一致 |

### R2-7 日常闲聊互动
| 项 | 内容 |
|---|---|
| 业务描述 | 拟人化友好交互，维系对话热度，提升留存 |
| 实现方式 | **Dify 专属人设 Prompt**：亲切、可爱、符合年轻人语境，可适度用网络热梗/温暖表达 |
| ⚠️ 合规红线 | 闲聊**不得对录取结果、签证结果、费用做任何承诺**；不得输出与知识库冲突的内容；避免过度拟人化引起误解 |
| 验收点 | 闲聊自然不生硬；一旦用户在闲聊中表露真实诉求，能被意图识别**拉回业务流程** |

## 三、⭐ 协作清单：哪些地方必须配合其他 Agent

> 这一节是本模块能否按时交付的关键。你的模块**天然依赖大量底座**，不要自己埋头重造。

### 3.1 与 P1（前端 + 研判）—— 依赖最重

| # | 协作事项 | 我要对方提供 | 我要交付对方 | 不约定会怎样 |
|---|---|---|---|---|
| 1 | **接口契约** | 统一响应体格式、错误码规范、鉴权方式（token/header） | 客服模块全部接口的请求/响应结构 + Mock 数据 | 前端做完了接口对不上，返工 |
| 2 | **前端客服端界面 + 业务卡片** | 三端共用组件库 | 卡片数据结构（推荐卡/报名表/知识卡/FAQ卡） | AI 返回结构决定不了，卡片渲染不了 |
| 3 | **登录/注册与访客身份** | 访客 → 意向客户的注册逻辑；**不登录能不能报名** | 报名接口对身份字段的要求 | 报名表没有 `customer_id`，报名无法落库 |
| 4 | **客户主键统一（务必冻结）** | 明确 `event_registration.customer_id` 关联的是 `sys_user.id` 还是 `crm_lead.id` | — | 与员工端客户数据对不上，报告口径混乱 |
| 5 | **研判结果复用** | 客户画像结论（学历、意向国家等字段） | 推荐接口的入参定义 | 推荐模块拿不到用户画像，只能瞎推 |
| 6 | **统一响应/异常/日志基座** | 全局异常处理器、日志组件、公共返回类 | 按基座实现我的 Controller/Service | 各写各的，不符合「企业级规范」评分项 |

### 3.2 与 P3（员工 Agent）—— 导流链路

| # | 协作事项 | 说明 |
|---|---|---|
| 1 | **客服转线索** | 客服会话识别出高意向客户 → 写 `crm_lead`（客户姓名、联系方式、背景、来源=客服）。需要双方约定字段映射与「什么算高意向」的判定口径 |
| 2 | **报名信息回写** | 活动报名名单要在员工端可查、可跟进 |
| 3 | **课程/活动数据由谁维护** | `course_project`、`event_lecture` 的录入入口放员工端还是甲方导入？决定我的接口是「只读」还是「读写」 |
| 4 | **多意图识别框架复用** | 员工端的意图路由（P3 负责 AI 对话能力）与客服端 7 意图**应共用一套框架**，不要各写一套 |

### 3.3 与 P4（学生 Agent）—— 共享资源

| # | 协作事项 | 说明 |
|---|---|---|
| 1 | **课程与项目表复用** | 学生端「增值转化（升学推荐）」与客服端「课程推荐」都用 `course_project`，表结构变更要同步 |
| 2 | **知识库边界划分** | 客服侧=公司信息/公司业务/留学政策/FAQ；学生侧=海外生活指南。**同一份《留学政策》可能两侧都要用**，需约定是共用同一知识库还是各自切片 |
| 3 | **推荐/营销话术生成** | 学生端「营销生成」与客服端「推荐话术」逻辑高度相似，可共用 Prompt 资产 |

### 3.4 与 P5（智能报告）—— 数据供给

| # | 协作事项 | 说明 |
|---|---|---|
| 1 | **埋点与日志口径提前约定** | 客服会话记录、意图日志、报名转化记录，是「全域客户经营分析报告」的原料。**要提前约定字段与口径**（什么叫意向客户、什么叫转化），否则报告取不到数 |
| 2 | **会话数据留存** | 建议新增 `cs_chat_session` / `cs_chat_message` / `cs_intent_log` 三张表（见第四节），这是报告的取数来源 |
| 3 | **转化归因** | 从「咨询某课程」到「报名/签约」的漏斗数据，需要客服侧打点 |

### 3.5 与全组：共享底座的归属（**最大的协作风险**）

参考《教育AI中台_分工与开发计划》里明确的原则：

> **按能力分层，不按模块包干。** 四个 Agent 共用「意图路由 + RAG + 数据表 + 触发器 + 权限」五块底座，若各人包干一个模块，会重复造四套底座。

而你小组的实际分工是 **p1~p5 按模块包干**，这与上述原则**存在张力**。落地建议：

- 由 **P1 负责「数据模型 + 接口契约 + 权限 + 统一工程基座」**并**先冻结**，其他人再并行做业务；
- **AI 对话框架（意图路由 / Dify 应用 / Prompt 资产管理）由 P3 统一建**，客服模块**复用**，不要自己搭一套 Dify 并行；
- **知识库建设**（切片/向量化/检索服务）如果没有专职人，建议**客服模块的公司信息/业务/政策/FAQ 知识库先由你牵头**，但要走**统一检索服务**，避免和员工端、学生端各建一个孤岛；
- 结论：**先开会冻结数据模型和接口契约，再动手写代码**，这是全组最高优先级的事。

## 四、数据库设计（客服模块相关表 + 需补充的表）

### 4.1 现有草稿中与客服相关的表

| 表 | 用途 | 备注 |
|---|---|---|
| `course_project` | 课程与项目（推荐用） | 建议补充：`target_country`、`education_level`、`duration`、`tuition`、`status` 字段，才能做规则推荐 |

### 4.2 建议新增的表（客服模块 + 报告取数）

```sql
-- 客服会话表
cs_chat_session(
  id, session_no, customer_id, channel, status,
  start_time, end_time, create_time
)

-- 客服消息表（对话明细，报告与质检原料）
cs_chat_message(
  id, session_id, role(user/assistant), content,
  intent_code,       -- 命中的意图（R2-1~R2-7）
  card_type,         -- 返回的卡片类型（推荐卡/报名卡/知识卡）

  create_time
)

-- 意图/转化日志（P5 报告漏斗原料）
cs_intent_log(
  id, session_id, customer_id, intent_code,
  converted(int),    -- 是否转化为线索/报名
  create_time
)

-- 推荐记录（可选，做推荐效果复盘）
cs_recommend_log(
  id, customer_id, session_id, project_ids, reason, create_time
)
```

> 交付要求：ER 图与字段说明要并进**数据库设计文档**，且与 P1 的「8 张核心表」保持同一套命名与主键规范。

## 七、企业级工程规范在客服模块的落地（评分点）

对照「统一响应、异常处理、日志、MVC 分层」四条：

```
cs_module/
├── controller/        # 只做参数校验 + 调用 service + 返回统一响应
│   ├── CsChatController.py
│   ├── CsEventController.py
│   └── CsCourseController.py
├── service/           # 业务逻辑（报名校验、推荐规则、导流）
│   ├── impl/
│   └── *.py
├── mapper/ (dao)      # 数据访问，只碰 SQL
├── model/ (entity)    # ORM 实体
├── schema/            # 请求/响应 Pydantic 模型（dto/vo）
├── client/            # Dify API 客户端封装（超时、重试、降级）
└── common/            # 复用全局：统一响应、异常、日志
```

**四条规范的具体体现：**

1. **统一响应**：所有接口返回 `ApiResponse.ok(data)` / `ApiResponse.fail(code, msg)`，禁止裸返回。
2. **异常处理**：自定义 `BizException(code, msg)`（如「活动已满员」「重复报名」「AI 服务不可用」）+ 全局异常处理器统一兜底，Controller 内不写 try-catch 业务分支。
3. **日志**：请求入参/出参日志、业务关键节点日志、**Dify 调用日志**（模型、耗时、token、是否命中知识库），带 `traceId` 串联全链路。
4. **MVC 分层**：Controller 薄、Service 厚、Mapper 只碰 SQL，禁止 Controller 直连 DAO 或写业务。

**AI 与传统功能的边界（老师要求第 3 点）：**
- **Dify 负责**：意图识别、RAG 检索问答、推荐话术生成、闲聊人设、防幻觉约束。
- **Python 后端负责**：活动 CRUD / 报名事务、课程数据查询与规则初筛、会话与日志落库、导流写 `crm_lead`、鉴权与权限。
- **原则**：**能确定性计算的（名额、重复报名、规则匹配）交给 Python；需要理解语言的（意图、生成、检索）交给 Dify。** 不要让大模型做本该由代码保证正确性的事。

## 十一、附录：三张业务表的归属确认（课程 / 活动 / 报名）

**结论：`course_project`、`event_lecture`、`event_registration` 三张表归客服 Agent（你），不属于企业模块。**

### 11.1 证据（甲方需求原文，逐条可查）

| 客户需求表 · **客服Agent** 需求拆解 | 「**活动报名闭环**：设计**活动表**，开发活动查询与报名接口，支持客户在对话中直接完成……预约，并将报名信息自动录入后台系统。」 | **客服 Agent** |
| 客户需求表 · **企业智能助手** 需求拆解 | 「需新建**四张**核心数据表：意向客户表、员工日报表、投诉反馈表、学生成绩表。」 | **不含**课程/活动表 |
| 客户需求表 · **学生智能助手** 需求拆解 | 「需新建**四张**关键数据表：学生行政服务表、心理健康画像表、心理预警表、售后反馈工单表。」 | **不含**课程/活动表 |

> 反证：企业模块的 4 张表 + 学生模块的 4 张表 = 8 张，正好对应分工计划里「8 张核心表建模与建库」，**课程/活动/报名三张表不在这 8 张之内**。

### 11.2 但「做」要分三层，不是全你一个人干

| 层面 | 内容 | 建议归属 |
|---|---|---|
| ① 表结构与字段设计（DDL） | 字段、类型、索引、约束、唯一键 | **你**（已产出《05_客服Agent模块_数据库建表语句.sql》） |
| ② 建库与纳入全组 ER 图 | 统一命名/主键规范、并入总库与数据库设计文档 | 与 **P1** 对齐：P1 出规范，你按规范建，再同步回总 ER 图 |
| ③ 数据来源与维护 | 课程/活动数据由谁录入、由谁更新 | ⚠️ **待组内确认**（见 11.4） |

### 11.3 与企业模块的边界（谁的表、走什么接口）

| 表 | 归属 | 与自己模块的交界 |
|---|---|---|
| `crm_lead` 意向客户 | **P3** | 你**写入**（P10 高意向转线索），P3 跟进；你需它补 5 个字段 |
| `employee_daily_report` 员工日报 | P3 | 无交集 |
| `student_score` 学生成绩 | P3 | 无交集 |
| `student_feedback_ticket` 投诉工单 | P3 / P4 | 无交集（属学生售后） |
| `course_project` 课程与项目 | **你** | P4 学生端「增值转化」**共用此表**，变更需同步 |
| `event_lecture` 活动与讲座 | **你** | 员工端可能需查询活动 |
| `event_registration` 活动报名 | **你** | 报名名单**回写后台**，员工端可查、可跟进 |

一句话：**表归你建、你定接口；数据被企业端消费。**

### 11.4 需要和组里确认的三个问题（建议本周例会提）

1. **活动/课程数据的录入入口放哪？** 员工端录入、甲方后台导入、还是先由你构造演示数据？→ 决定你的接口是「只读」还是「读写」。
2. **报名名单怎么给员工端？** 是你提供查询接口，还是直接读同一张表？→ 决定权限与接口归属。
3. **建库走谁的流程？** 你直接建，还是等 P1 的统一 ER 与命名规范？→ 决定开工时间。

> 如果组里最终决定把这三张表挪给 P3 或 P1，也可以，但必须**明确「谁建表、谁维护数据、谁定接口」三件事**，否则会出现「两边都以为对方做」的真空。
