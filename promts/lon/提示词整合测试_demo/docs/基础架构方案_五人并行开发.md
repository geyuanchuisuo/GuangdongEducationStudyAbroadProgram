## 二、模块划分与职责边界（五人分工）

### 2.1 模块总览

| 模块 | 负责人代号 | 核心职责 | AI 依赖 |
|------|-----------|---------|---------|
| **M0 公共基础设施** | P1（兼） | 认证鉴权、统一响应/异常、日志追踪、数据权限、AI网关、文件存储、通知中心、审批引擎、事件总线、前端初始化、数据库规范 | 无 |
| **M1 客户模块（含研判）** | P1 | 客户注册/登录、客户画像研判、客户 CRUD、客户状态流转、研判结果管理 | 研判 Agent（Dify） |
| **M2 客服 Agent 模块** | P2 | 7 大场景对话、知识库 RAG、课程推荐、活动报名闭环、高意向转线索、会话日志 | 客服 Agent（Dify） |
| **M3 员工模块** | P3 | 意向客户管理（CRM）、日报管理、成绩录入、审批处理、组织架构、新人指引、口述日报 | 员工 Agent（Dify） |
| **M4 学生模块** | P4 | 请假申请、心理关怀/预警、售后反馈、学业考务、进度追踪、生活支持、增值转化 | 学生 Agent（Dify） |
| **M5 智能报告模块** | P5 | 5 类报告生成、经营看板、数据聚合、报告权限控制 | AI 分析（摘要/归因） |

### 2.2 模块间依赖关系（单向，禁止循环）

```
M0 公共基础设施
 ↑  ↑  ↑  ↑  ↑
 │  │  │  │  │
M1 → M2 → M3 → M5（报告只调各模块暴露的查询接口，不直接查别人的表）
 │         ↑
 └─── M4 ──┘（学生模块与员工模块通过事件通信，不直接依赖）
```

**关键原则**：
- 报告模块（M5）**只调各模块已暴露的查询接口取数**，不直接查别人的表
- 模块间业务流转**走事件总线**，不直接 import 对方 service
- 所有模块**共用 M0 的 AI 网关**，禁止直连 Dify

## 三、公共基础设施（M0）— 必须优先架构

### 3.1 统一用户与权限体系

```
sys_user
├── id (PK)
├── username (唯一)
├── password_hash
├── real_name
├── user_type: PROSPECT | STUDENT | EMPLOYEE | MANAGER | ADMIN
├── permissions: JSON  ← 一期先加字段，二期做配置界面
├── phone (唯一，客户去重标识)
├── department
├── status: active | disabled
├── created_at / updated_at
```

**权限落地策略**：
- 一期：`user_type` 粗判 + 数据隔离（员工只看名下客户 `owner_employee_id = current_user.id`）
- 表结构预留 `permissions` JSON 字段，避免二期改表
- 统一 `@require_user_type([...])` 装饰器 + `@require_permission("xxx")` 装饰器

### 3.2 统一 AI 网关

```python
# services/ai_service.py — 唯一入口
class AIService:
    async def chat(
        self,
        agent: AgentType,      # CUSTOMER | EMPLOYEE | STUDENT
        message: str,
        session_id: str,
        context: dict = None   # 注入变量（slots、knowledge 等）
    ) -> AIResponse:
        ...

    async def chat_stream(...) -> AsyncIterator[str]:
        ...  # SSE 流式支持
```

- 各模块只调 `ai_service.chat(agent_type, ...)`
- 统一处理：超时、重试、降级、日志、token 计量
- Dify 三个 Agent Key 集中管理

### 3.3 事件总线（轻量级，数据库事件表）

```sql
CREATE TABLE sys_event (
    id BIGINT PK AUTO_INCREMENT,
    event_type VARCHAR(64) NOT NULL,    -- 事件类型编码
    source_module VARCHAR(32) NOT NULL, -- 发出模块
    payload JSON NOT NULL,              -- 事件数据
    status VARCHAR(16) DEFAULT 'pending', -- pending/consumed/failed
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

**一期冻结的核心事件契约**：

| 事件类型 | 发出方 | 消费方 | 核心字段 |
|---------|--------|--------|---------|
| `customer.registered` | M1 客户 | M3 员工（待办） | customer_id, phone, name |
| `customer.converted_to_student` | M1/M3 | M4 学生, M5 报告, M3 待办消除 | customer_id, student_id |
| `leave.approved` / `leave.rejected` | M3 员工 | M4 学生, 通知中心 | student_id, leave_id, status |
| `psych_alert.created` | M4 学生 | M3 员工/管理层待办, 通知中心 | student_id, risk_level, reason |
| `complaint.resolved` | M3 员工 | M4 学生, 通知中心 | ticket_id, student_id, solution |
| `lead.transferred` | M2 客服 | M3 员工（跟进） | lead_id, customer fields |

### 3.4 审批工作流引擎（通用审批单表）

```sql
CREATE TABLE sys_approval (
    id BIGINT PK AUTO_INCREMENT,
    approval_type VARCHAR(32) NOT NULL,  -- convert_student / leave / late_report
    initiator_id BIGINT NOT NULL,
    approver_id BIGINT,
    target_id BIGINT,                    -- 关联业务对象 ID
    status VARCHAR(16) DEFAULT 'pending', -- pending/approved/rejected
    remark TEXT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

4 种审批场景全部走这张表 + 统一接口，禁止各自实现。

### 3.5 通知中心（双通道）

**通道 A：Agent 实时推送（WebSocket/SSE）**
- 用于：心理预警即时通知、审批结果实时推送、待办提醒
- 前端保持 WebSocket 长连接，后端主动推送

**通道 B：站内消息（数据库持久化）**
- 用于：系统通知、状态变更、历史消息查询
- 写入 `sys_notification` 表，前端轮询或分页查询

```sql
CREATE TABLE sys_notification (
    id BIGINT PK AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    type VARCHAR(32) NOT NULL,  -- approval/todo/academic/psych_alert/status/system
    title VARCHAR(255),
    content TEXT,
    is_read BOOLEAN DEFAULT FALSE,
    related_type VARCHAR(32),   -- 关联业务类型
    related_id BIGINT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

统一 `notify(user_id, type, title, content, related)` 服务接口，同时触发 WebSocket 推送。

### 3.6 其他公共组件

| 组件 | 说明 |
|------|------|
| **统一响应** | `ApiResponse.ok(data)` / `ApiResponse.fail(code, msg)`，含 traceId |
| **统一异常** | `BizException(code, msg)` + 全局异常处理器 |
| **日志追踪** | request_id 中间件，全链路 traceId |
| **数据权限** | 查询装饰器 `@data_scope`，员工自动过滤 `owner_employee_id` |
| **文件存储** | MinIO 统一 upload/download，按 `模块/日期/` 分目录 |
| **分页/排序** | 统一 `PageParams` / `PageResult` |
| **错误码** | 按需求文档 §14.3 完整实现（补 40005、40102、40901） |

## 五、模块解耦设计

### 5.1 接口契约规范

每个模块对外暴露**查询接口**，其他模块通过接口取数：

```
M1 客户模块对外接口：
  GET  /api/v1/crm/leads/{id}           → 客户详情
  GET  /api/v1/crm/leads/stats          → 客户统计（报告用）
  GET  /api/v1/crm/assessments/{id}     → 研判结果

M2 客服模块对外接口：
  GET  /api/v1/cs/courses               → 课程列表
  GET  /api/v1/cs/events                → 活动列表
  GET  /api/v1/cs/sessions/stats        → 会话统计（报告用）

M3 员工模块对外接口：
  GET  /api/v1/employee/reports         → 日报列表
  GET  /api/v1/employee/reports/summary → 日报汇总（报告用）

M4 学生模块对外接口：
  GET  /api/v1/student/psych/stats      → 心理统计（报告用）
  GET  /api/v1/student/tickets/stats    → 投诉统计（报告用）
```

### 5.2 事件驱动的业务流转

```
客户注册 → [customer.registered] → 员工端出现待办
    ↓
客服识别高意向 → [lead.transferred] → CRM 新增线索
    ↓
员工申请转化学生 → sys_approval → 经理审批
    ↓
审批通过 → [customer.converted_to_student] → 学生端开通 + 报告更新
    ↓
学生请假 → sys_approval → 员工审批 → [leave.approved] → 学生收到通知
    ↓
心理预警 → [psych_alert.created] → 员工/管理层待办 + 即时通知
    ↓
投诉处理完成 → [complaint.resolved] → 学生收到反馈通知
```

### 5.3 共享数据访问规则

| 数据 | 维护方 | 读取方 | 访问方式 |
|------|--------|--------|---------|
| `course_project` | M2 客服 | M4 学生（增值转化）、M5 报告 | M4/M5 调 M2 接口 |
| `event_lecture` | M2 客服 | M3 员工（查看名单）、M5 报告 | M3/M5 调 M2 接口 |
| `crm_lead` | M1 客户 | M3 员工（跟进）、M5 报告 | M3/M5 调 M1 接口 |
| `student_psych_*` | M4 学生 | M5 报告 | M5 调 M4 接口 |

| `student_feedback_ticket` | M4 学生 | M3 员工（处理）、M5 报告 | M3/M5 调 M4 接口 |

**AI vs 传统代码边界**：

- **代码负责**：CRUD、名额校验、重复拦截、规则匹配、权限控制、数据落库、事务处理
- **原则**：能确定性计算的交给代码；需要理解语言的交给 AI

- Agent 对话窗口**三端复用**同一组件，通过 `agent_type` 区分
- 路由守卫根据 `user_type` 动态加载菜单
- 业务卡片数据结构与后端 P13 卡片 JSON 对齐
