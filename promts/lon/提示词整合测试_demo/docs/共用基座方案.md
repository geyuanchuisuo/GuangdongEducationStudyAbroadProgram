### Dify 边界四条铁律

1. **权限与数据隔离绝不写在提示词里**：员工"仅名下客户"由后端 API 按登录态强制校验，Dify 透传用户 token；提示词可被注入绕过。
2. **禁止 Dify 直连数据库 / NL2SQL**：员工助手口语查数一律调后端受控查询接口。
3. **所有 LLM JSON 回传必须过 schema 校验**：不合格自动重试（≤2 次），仍失败转人工/记录异常；研判结果记录 Dify 应用版本号。
4. **协作纪律**：一个应用一个负责人；HTTP 工具契约（后端接口清单）由第 0 阶段冻结后，各模块才可并行。

### 模块与 Dify 应用映射

| Dify 应用 | 类型 | 触发方 | 调用的后端工具（HTTP 节点） |
|---|---|---|---|
| M1 研判 | Workflow | 后端（录入/转线索/注册事件） | 研判结果回写接口 |
| M2 客服 | Chatflow | 访客网页 | FAQ 召回、候选项目初筛、活动查询、报名提交、转线索写入 |
| M3 企业助手 | Chatflow | 员工/管理层网页悬浮窗 | 客户查询、跟进写入、日报提交、待办查询、审批操作、组织查询 |
| M4 学生助手 | Chatflow | 学生网页 | 请假提交、工单提交、进度查询、考务查询、情绪写入 |
| M5 报告 | Workflow | 后端定时任务 | 统计取数接口、报告落库接口 |

## 4. 统一数据模型（28 张表）

## 7. 接口契约规范（冻结后 5 人并行）

- 前缀 `/api/v1`；统一响应体：`{ "code": 0, "message": "ok", "data": {...} }`
- 错误码分段：`1xxx` 认证权限 / `2xxx` 参数校验 / `3xxx` 业务规则 / `4xxx` Dify/LLM / `5xxx` 系统
- 分页参数统一 `page` / `page_size`，返回 `total`
- Dify → 后端的工具接口单独前缀 `/api/v1/dify-tools/*`，必须携带用户 token，后端按数据范围过滤
- 后端 → Dify 使用应用级 API Key，Key 按应用隔离、存环境变量
- OpenAPI 文档（FastAPI 自动生成）即契约，变更需 owner 评审

## 11. 种子数据规范

- 组织：五个事业部（双元制/智能装备/课后服务/研学服务/科技赛事）+ 部门经理
- 账号：普通员工 ≥6（每部门 ≥1）、经理 2、总裁 1；测试密码统一规则写入文档
- 客户：≥30，覆盖三种来源渠道、六态全状态、含 1 组批次内同号合并、1 条微信号待补全线索；**手机号全部合规**（示例文档中 10 位号码不采用）
- 研判：每个结论档位 ≥2 条样例（用 3 份测试简历跑通解析→研判链路）
- 项目：新加坡 7 个班型 + 中德 1 个项目，年龄/学历规则按研判规则配置
- FAQ：36 条；活动：≥3 场（含名额将满 1 场）
- 学生侧：请假/工单（三类型）/心理预警（三等级）/成绩/教务节点各 ≥3 条
- 日报：近 7 天样本含草稿、已提交、补报待审批

## 14. 风险说明

1. **Dify 全量依赖**：5 个应用均在 Dify，若 Dify 服务宕机，员工/学生 Agent 功能不可用——通知中心站内信兜底已设计；建议部署后做压测与备份策略
2. **提示词注入**：研判/客服提示词已内置防注入条款，但数据隔离的最终防线在后端 API 校验，联调时必须用越权用例测试
3. **知识库口径**：政策指南含大量与公司项目口径不一致的数字，必须严格分源并在 P3/P3-a 中约束引用范围
4. **研判一致性**：同一客户重跑研判结论可能波动，列表排序以最新一次为准，历史可追溯
