# 第一部分：公共底座方案（全员共享基座，先行交付）

> 使用方式：底座以 Git 仓库初始基线形式交付，五人各自 clone 后按模块分支开发。
> 底座包含四件套：**① 后端工程骨架 ② 前端 Monorepo 骨架 ③ 契约目录（冻结） ④ docker-compose 环境**。

## 1. 总体架构

```
┌──────────────── 接入层 ────────────────┐
│ apps/portal(C端)  apps/staff(员工端)  apps/student(学生端) │
│        └──── packages: ui组件库 / ChatWindow对话窗 / CardRenderer卡片 / api-client ────┘
├──────────────── API 层 ────────────────┤
│  /api/v1/{auth,org,crm,judge,cs,staff,stu,report,notify,kb,system}      │
│  统一响应体 · 全局异常 · TraceId日志 · JWT+RBAC · 行级数据权限              │
├──────────────── 模块层 ────────────────┤
│  judge │ cs │ staff │ stu │ report                                    │
│  ──── 模块间只允许经内部 Facade 调用，禁止跨模块读写表 ────                  │
├──────────────── 公共底座 ──────────────┤
│ 认证/RBAC/数据权限 │ LLM网关 │ RAG检索 │ 审批流引擎                       │
│ 消息中心/WS推送   │ 文件解析 │ 定时任务 │ 操作日志                        │
│ Excel导入导出   │ 数据字典 │ 种子数据 │                                │
├──────────────── 外部服务 ──────────────┤
│  Dify(chatflow×3 + 知识库)     DeepSeek-V3 API                          │
└────────────────────────────────────────┘
```

架构形态：**模块化单体**（单后端进程、严格包边界、内部 Facade 解耦）。理由：模块间数据关联极密，微服务的分布式事务成本远超收益；模块边界即未来服务边界，可平滑演进。

## 3. 工程基座规范（所有模块强制遵守）

- **统一响应体**：`{ code, message, data, traceId, timestamp }`；成功 `ApiResponse.ok(data)`，失败 `ApiResponse.fail(code,msg)`；禁止裸返回。
- **异常体系**：`BizException(code, msg)` + 全局异常处理器兜底；Controller 内不写业务 try-catch。
- **MVC 分层**：controller（参数校验+调 service）/ service（业务）/ mapper（只碰 SQL）/ model（ORM）/ schema（Pydantic 出入参）。禁止 Controller 直连 mapper。
- **日志**：请求/响应、业务节点、**LLM 调用日志**（模型/耗时/token/是否命中知识库）；`traceId` 全链串联（中间件注入，写进每条日志与响应体）。
- **配置**：`.env` + 环境分层（dev/test/prod）；密钥不落库、不落仓。

## 4. 认证、RBAC 与数据权限（Q4/Q5）

- **统一用户表 `sys_user`**：`id, phone(唯一), name, user_type(PROSPECT/STUDENT/EMPLOYEE), status(待开通/正常/停用), password_hash, dept_id, ...审计字段`。
- **注册流程**：访客匿名对话（发 guest_token）；报名/留资时以手机号注册 → `status=待开通`；员工审核开通 → 正常；员工发起转化申请 + 经理审批 → `user_type: PROSPECT→STUDENT`。
- **认证**：JWT（access 2h + refresh 7d），登录态存 Redis。
- **角色**：`role`（staff / manager；二期预留 hr/director）。权限点按菜单+按钮注册到 `sys_permission`。
- **行级数据权限（核心）**：CRM 数据按 `owner_id` 隔离——普通员工仅名下客户；管理层一期全域。【二期】按部门隔离。实现位置：**统一查询基类 `OwnedQuery` 强制注入 owner 条件**，各模块不得自行拼装；**Agent 工具调用复用同一套数据权限**（一处定义，页面与 Agent 两处生效）。
- **Agent 权限感知**：底座提供 Agent 工具注册器，工具声明所需角色/数据范围，执行前统一鉴权；未授权指令返回"权限不足/请联系HR"。

## 5. 数据库规范与共享表（底座建表）

命名：`模块前缀_表名`，主键 `id` BIGINT 自增，统一审计字段 `create_by/create_time/update_by/update_time/is_deleted`。

| 底座自带表 | 说明 |
|---|---|
| `sys_user` / `sys_role` / `sys_permission` / `sys_user_role` | 用户与权限 |
| `org_dept` | 组织架构（来源：企业信息.docx 五大事业部 + 新人指南部门表） |
| `approval_flow` / `approval_task` | 通用审批流（见 §7） |
| `message` | 站内信（审批结果/预警/公告，离线兜底） |
| `operation_log` | 操作日志（客户状态变更/审批/权限调整，AOP 采集） |
| `sys_dict` / `sys_dict_item` | 数据字典（客户状态、工单状态、情绪标签等枚举） |
| `sys_file` | 上传文件登记 |
| `llm_call_log` | LLM 调用日志 |
| `kb_document` | 知识库文档登记（与 Dify 知识库映射、标签、授权 Agent） |

业务模块表（judge/cs/staff/stu/report）在各自模块内建，但**必须遵守本命名与审计规范**，DDL 需进 `contracts/ddl/` 评审后合并。

## 6. LLM 网关（Q3/Q10）

- `llm_client`：直调 DeepSeek-V3（chat + JSON mode），供研判、摘要、日报结构化、报告归纳等**结构化场景**；强制 JSON Schema 校验 + 失败重试/修复。
- `dify_client`：封装 Dify Chatflow 调用（客服/企业助手/学生助手 3 个 app），流式响应、会话变量透传、超时/重试/**降级**（Dify 不可用时：客服走 FAQ 关键词匹配兜底；企业助手返回"AI暂不可用"+站内信兜底）。
- `asr_client`：仅接口抽象，一期不实现【二期】。
- 全部调用写 `llm_call_log`；Prompt 资产统一存放 `contracts/prompts/`，编号+版本（如 JUDGE-v1.0、P3-v1.2），禁止散落在代码里。

## 7. 通用审批流引擎

一期审批场景：请假（学生→负责员工）、留学生转化（员工→经理，支持批量通过）、日报补报（员工→经理）。【二期】人事审批链。

- 设计：`approval_flow`(类型/申请人/当前节点/状态) + `approval_task`(节点/审批人/动作/意见)；按 `biz_type` 注册审批定义；状态机：待审批→通过/驳回。
- 通知链路（员工模块明确要求）：审批结果 → 站内信 + Agent 推送 → 学生端状态变更 → 员工端待办消除。
- 管理层审批列表支持**批量操作**。

## 8. 消息中心与主动推送（Q12）

- WebSocket 服务（FastAPI WS + Redis pub/sub 频道）：在线实时推送待办/预警/审批结果/Agent 主动提醒。
- 离线写 `message` 站内信；登录时拉取未读（员工模块要求"登录拉取+关键动作后实时推送"）。
- **事件触发器框架**：业务模块发布领域事件（新工单/新审批/情绪预警/客户状态变更…）→ 底座订阅生成待办与推送；Agent 不可用时站内信兜底。

## 9. RAG 知识库服务

- 知识库清单与标签：

| 知识库 | 数据源 | 挂载 Agent |
|---|---|---|
| 公司信息 | 企业信息.docx | 客服 |
| 公司业务 | 新加坡/中德两计划.docx | 客服 |
| 留学政策 | 新加坡/德国政策指南.docx | 客服（【二期】学生端可复用，**同一文档只入库一次**，按标签授权） |
| FAQ | 常见问答对 37 条 → `cs_faq` 结构化 | 客服 |
| 新人指南 | 公司新人指南.docx | 企业助手 |
| 海外生活指南 | 待甲方提供，先占位 | 学生助手 |

- 流水线：文档 → 结构化切片 → Dify 知识库（向量化） → 统一检索接口 `kb.search(tag, query, top_k)` → **强制引用出处 + NO_ANSWER 兜底**；政策/费用类高风险输出走防幻觉约束 Prompt（P3-a）；敏感信息（银行账号）经 P12 改写拦截，对外引导"联系顾问获取"。
- FAQ 采用**两级召回**：关键词/相似问法精确匹配秒回 → 未命中走语义匹配（P5，confidence≥0.75）→ 仍未命中走 RAG → 兜底话术。

## 10. 文件解析服务

- 支持文本 / PDF / Word / Excel / 照片录入：PDF/Word/Excel 用解析库（pypdf/python-docx/openpyxl）；照片一期用多模态 LLM 提取文字。
- 统一入口 `file.parse(file) -> text`，输出交研判/信息抽取。限制：≤10MB、≤50 页（可配置）。

## 11. 定时任务（APScheduler，一期）

- 报告生成（周报/月报定时产出 + 手动触发）。
- **客户流失判定**：每日扫描"首次注册登录后 90 天无再登录且无员工提交记录"→ 置流失；再次登录或有员工提交 → 移出流失重计意向（报告已确认口径）。
- 待办/跟进提醒扫描。【二期】可切 Celery。

## 12. Excel 导入导出与种子数据

- 导出：客户列表/日报/投诉记录（员工模块要求）；导入：批量客户名单（研判批量场景，批次内同号合并、冲突值保留 `conflicts` 提醒人工确认）。
- **种子数据脚本**（员工模块硬性要求"数据库直接录入足量测试数据"）：覆盖组织/员工/客户/跟进/日报/学生/成绩/请假/工单/心理/考务/进度/活动/FAQ/课程；含 3 份测试简历的研判样例（曹文栋/许剑鸿/黄学勤）。

## 13. 前端底座（Q8/Q9/Q12）

- Monorepo + 三入口；`packages/chat` 的 **ChatWindow** 三端共用（不同 Agent 配置与权限），支持流式输出、卡片渲染、多轮上下文（一期 5 轮）。
- **业务卡片协议 5 类**（`contracts/cards/`）：`recommend 推荐卡 / signup 报名卡 / knowledge 知识卡 / faq卡 / confirm 二次确认卡`。二次确认卡同时服务客服报名与企业助手指令式处理（"即将执行：给张三添加跟进记录… [确认][取消]"）。
- 口述日报一期形态：文字输入框 → AI 结构化整理（今日工作/明日计划/问题与反馈模板）→ 确认 → 提交。
- `api-client` 统一封装 token 刷新、traceId、错误提示；WS 封装含断线重连。

## 14. 部署（Q10）

`docker-compose.yml`：mysql8 / redis7 / dify（api+worker+web+db+weaviate）/ backend / nginx（前端静态资源 + /api 反代 + /ws）。资源限额备注；`.env.example` 提供全部配置样例（含 DEEPSEEK_API_KEY）。

## 15. 基于底座的模块开发规范（合并约定）

1. **契约先行**：模块开发前先向 `contracts/` 提交 DDL 草案 + OpenAPI 草案 + 事件定义，评审冻结后开发；前端不等后端，用 Mock 先行。
2. **解耦铁律**：① 跨模块只允许调对方 Facade（service 接口），禁止 import 对方 mapper、禁止跨模块 JOIN；② 每张表唯一属主；③ 跨模块动作用 Facade 同步调用 + 领域事件异步通知，不共享表轮询。
3. **API 前缀**：`/api/v1/{module}/...`；统一响应/异常/日志不得绕过。
4. **Git 流程**：`main`（保护）← `develop` ← `feature/{module}-*`；底座更新走 `base/*` 分支合并入 develop，各模块 rebase 拉取；合并前过契约兼容检查 + 全量冒烟。

# 第二部分：五模块方案（按 agent_demo 分工）

## 模块一：客户研判 judge（对应 agent_demo/judge）

- **职责**：多形态输入（纯文本/文件/客服对话记录/注册信息/批量名单）→ 依据内嵌《用户画像研判规则》对 singapore/germany 两产品独立研判 → 严格 JSON 输出。
- **实现**：后端直调 DeepSeek（不走 Dify）；Prompt 资产化（JUDGE-v1.0 入 `contracts/prompts/`）；输出 JSON Schema 校验。
- **规则要点**：先有效性校验（无效输入/手机号不合规：仅接受 1 开头 11 位大陆手机号）→ 信息提取（严禁编造）→ 逐产品四档结论（matched/partial/pending/not_matched）+ 逐维度证据 → 硬淘汰线（中德：年龄18-35、高中及以上已毕业、无犯罪记录）→ 推荐排序（matched/partial 按匹配度，第一即主推）→ missing_info / customer_overview / follow_up_advice；批次内同号合并、冲突保留。
- **表（属主 judge）**：`judge_result`（customer_id、双产品结论、维度证据 JSON、matched_programs、missing_info、overview、advice、原始输入快照、Prompt 版本）。
- **对外 Facade**：`assess(input)->json`、`assess_batch(list)`、`get_result(customer_id)`。
- **消费方**：crm（录入即研判）、cs（注册/对话触发）、report（画像三类统计直接采用最终结论）。

## 模块二：客服Agent kefu（对应 agent_demo/kefu）

- **职责**：对外获客入口：7 大场景 + 活动报名完整闭环 + 高意向转线索 + 4 类数据落库。
- **Dify chatflow（P0-P13 提示词集直接可用）**：P1 意图路由（R2-1~R2-8）→ 各分支（RAG 问答/政策强防幻觉/FAQ 两级召回/推荐/活动/闲聊年轻化人设）→ P10 高意向判定 → P11 会话摘要；P12 敏感信息改写兜底。
- **Python 负责确定性逻辑**（AI 与传统功能边界）：活动 CRUD、报名事务（**名额并发校验**、重复报名拦截、身份校验）、课程规则初筛（学历+意向国家→候选项目，模型只做话术）、转线索写库。
- **表（属主 cs）**：`cs_chat_session`、`cs_chat_message`、`cs_intent_log`、`cs_faq`、`course_project`（种子数据自业务文档整理）、`event_lecture`（管理端维护界面+演示数据）、`event_registration`（customer_id→sys_user.id）。
- **对外 Facade**：`transfer_lead()`（经 crm Facade 写 crm_lead，来源=客服会话）、会话/意图/报名数据查询（供 report）、`course_project` 查询（学生端增值转化共用，变更需同步）。
- **前端**：apps/portal（公开主页 + 客服对话窗 + 注册 + 活动报名卡）。

## 模块三：企业智能助手 emplo（对应 agent_demo/emplo）

- **职责**：员工端 CRM + 工作台 + 日报 + 审批 + 组织/新人指引 + 学生业务综管 + 经营看板 + 企业 Agent。
- **范围**：功能矩阵一期 38 项（工作台待办、客户录入/查询/状态机/漏斗、日报（含文字输入 AI 结构化、草稿、次日0点前补提、补报审批）、管理层看板/日报汇总/批示（仅该员工+上级可见）/批量审批/员工管理/客户再分配、组织架构（联系方式脱敏+二次确认）、新人指引（RAG+引导）、消息中心、操作日志）。
- **客户状态机**：新录入→跟进中→意向强烈→已签约→已入学→已流失（含流转约束，变更写操作日志，实时同步漏斗）。
- **企业 Agent**（Dify chatflow）：意图识别→权限校验→功能路由；数据隔离（员工仅名下/管理层全域，复用底座行级权限）；指令执行二次确认卡；多轮≤5 轮；主动提醒（登录拉取+事件推送）。
- **表（属主 staff）**：`crm_lead`（含 owner_id、来源、状态机）、`crm_follow_record`、`employee_daily_report`（结构化内容 JSON/草稿/批示）、`student_score`、经营看板视图。（审批流复用底座 approval_*）
- **对外 Facade**：客户/跟进/日报/组织查询与操作（供 report、stu、Agent 工具）。
- **前端**：apps/staff（员工/管理层双角色菜单）。

## 模块四：学生智能助手 stu（对应 agent_demo/stu；基线按 Q6）

- **职责**：在读服务闭环：请假审批、心理关怀（情绪疏导+预警）、售后工单、考务查询、留学进度追踪、生活知识库、增值转化。
- **关键流程**：
  - 请假：页面/Agent 提交 → 同时段冲突校验 → 审批流 → 结果站内信+Agent 推送。
  - 心理关怀【部分补全】：Agent 对话疏导 + 情绪标签/评分写 `psy_profile`；低于阈值 → `psy_warning` 即时通知负责员工（不等周报）→ 员工端生成心理关怀待办 → 标记已沟通/已转介/已解决 → `care_record`。
  - 售后工单：提交（长篇投诉 AI 摘要）→ 待处理→处理中→已反馈 → 结果回流学生端；**一期不分类**（Q1）。
  - 进度追踪：材料审核→申请提交→收到Offer→签证办理→行前准备→已入学（员工端更新，学生端只读）。
  - 增值转化【补全】：基于画像/进度识别升学意向 → 复用 `course_project` 推荐 → 营销话术生成。
- **表（属主 stu）**：`student_leave`（或并入 approval_flow）、`psy_profile`、`psy_warning`、`care_record`、`feedback_ticket`、`study_progress`、`exam_schedule`【补全：考务字段】。
- **对外 Facade**：风险事件/工单/请假/进度查询（供 report、staff 待办、Agent 工具）。
- **前端**：apps/student。

## 模块五：智能报告 intel_report（对应 agent_demo/intel_report）

- **职责**：5 类报告的定时生成与查看，口径全部按已确认规则落地：
  - **全域客户经营分析（周/月报）**：意向=注册登录∪员工提交、手机号去重、新增按首次时间、成交以状态更新为准、流失=90天规则+回流、同比环比；画像按两产品分别统计"符合/不符合/信息不足"（直接采用 judge 最终结果，分母=该产品该周期全部意向客户）；一期不分析流失原因【二期：高价值客户标准】。
  - **员工日报汇总（日/周）**：按部门汇总团队进展/产出/风险 + 应提交/已提交/未提交人数；周报对比上周；**不展示个人明细、不评价个人**。
  - **学生心理健康周报**：整体态势+风险人数+周变化+考试/假期节点解读；高风险即时通知负责人（走 stu 事件，不等周报）；管理层可见个案，顾问/老师按职责见相关个案。
  - **投诉处理周报**：只统计正式投诉、**不分类**（Q1）；AI 识别低评分/高风险候选 → **投诉负责人复核后才展示**；时效=提交至首次响应；>7 天=长期未解决；未评价单列。
- **实现**：定时任务 + 手动触发；各模块 Facade 只读取数（不拥有业务表）；客户口径实现为可复用 SQL 视图；AI 归纳（进展/风险提炼）走 llm_client，**事实/趋势/AI归纳/建议分区呈现**，指标带口径说明与统计周期。
- **表（属主 report）**：`report_instance`（类型/周期/内容 JSON/生成状态/生成时间）。
- **前端**：嵌入 apps/staff 管理层菜单（经营看板入口跳转）。
